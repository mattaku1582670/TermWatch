# 実装上の判断記録（DECISIONS）

要件定義書（`TermWatch_Requirements_v1.0.md`）と実装指示に明記されていない細部について、
実装時に行った判断とその理由を記録する。

---

## D-001: 実行コマンドの解決に PATH / PATHEXT の自前探索を使う

**判断**: `node-pty` へ渡す実行ファイルを、PATH と PATHEXT を自前で探索して解決する。
`.cmd` / `.bat` の場合だけ `cmd.exe /d /s /c <実体パス> <引数...>` の形で起動する。

**理由**: Windows の `CreateProcess` はバッチファイルを直接実行できない。
`codex` や `claude` は npm の bin シム（`.cmd`）であることが多く、直接指定すると起動に失敗する。

**安全性**: いずれの場合も引数は argv 配列のまま渡し、コマンド文字列を結合しない。
`/d` で AutoRun（レジストリの `Command Processor\AutoRun`）を無効化する。
`.ps1` の直接実行は拒否し、`powershell -File` を使うよう案内する。

---

## D-002: 出力バッファはチャンク単位で保持し、破棄もチャンク境界で行う

**判断**: リングバッファは「行」ではなく PTY から受け取ったチャンクを単位として保持する。
表示行数の上限はチャンク内の改行数を数えて近似的に適用し、加えて総バイト数の上限
（既定は `maxLines * 512`、最小 1 MiB、最大 64 MiB）も設ける。直近 1 チャンクは
上限を超えていても破棄しない。

**理由**: 行単位で切ると ANSI エスケープシーケンスの途中で分断され、
再接続時にスナップショットを流し込んだ際の描画が壊れる。実装指示でも
「行数ベースのリングバッファ実装がANSIシーケンスの途中切断を招く場合は、
安全なチャンク保持と表示行上限を組み合わせる」ことが許容されている。

**副作用**: 保持される表示行数は指定値ちょうどではなく「指定値以下の直近チャンク群」になる。
また、改行を含まない巨大な単一チャンクはバイト上限まで保持される。
1 つの ANSI シーケンスが 2 チャンクにまたがって届いた場合、その境界で破棄が起きると
分断されうる（頻度は極めて低く、xterm.js 側が不完全なシーケンスを読み捨てる）。

---

## D-003: スナップショットとライブ出力の境界にシーケンス番号を使う

**判断**: 各出力チャンクへ 1 から始まる単調増加のシーケンス番号を割り当てる。

- クライアントは接続直後に `resume { lastSeq }` を送る。
- サーバーは `snapshotSince(lastSeq)` の結果を `snapshot { data, seq, truncated }` として返す。
- 以後のライブ出力は `output { data, seq }` で送り、クライアントは `lastSeq` を更新する。
- 要求範囲の一部が既に破棄されている場合は `truncated: true` を立て、欠落を隠さない。

**理由**: スナップショット送信中に発生した出力の取りこぼしや二重表示を防ぐため。
サーバーは `resume` を受け取るまでそのクライアントへ配信を開始しない（`ready` フラグ）ので、
スナップショットより前のライブ出力が混ざることもない。

## D-004: ペアリングコードは 30 文字集合 × 8 文字（約 39.2 bit）

**判断**:

| 項目 | 値 |
|---|---|
| 文字集合 | `23456789ABCDEFGHJKMNPQRSTVWXYZ`（Crockford Base32 から `0` `1` を除いた 30 文字） |
| 長さ | 8 文字（表示は `XXXX-XXXX`） |
| エントロピー | log2(30^8) ≒ **39.2 bit** |
| 有効期限 | 起動から 10 分、または最初の認証成功の早い方 |

**理由**: Crockford Base32 は `I` `L` `O` `U` を既に除外している。さらに `0` `1` を除くことで
`0`/`O`、`1`/`I` の読み間違いを完全に排除し、スマートフォンでの手入力を容易にした。
8 文字はハイフン区切りで一目で読める上限に近い。

39.2 bit は単独では総当たり可能な水準だが、
(1) dev tunnels のアカウント認証を通過した攻撃者にしか試行機会がない、
(2) 連続 5 回の失敗でロックアウト（30 秒から倍化、上限 15 分）、
(3) 有効期限が 10 分、
の 3 点により実効的な総当たりは成立しない。

## D-005: Origin 検証は同一オリジンのみ。devtunnels のワイルドカード許可はしない

**判断**: `Origin` のホスト部が `Host` または `X-Forwarded-Host` と一致する場合だけ許可する。
`*.devtunnels.ms` のようなワイルドカード許可は**行わない**。`Origin` が無い接続は拒否する。

**理由**: ワイルドカードを許すと、攻撃者が自分の dev tunnel 上に置いたページから
利用者の `127.0.0.1:43821` へクロスサイト WebSocket 接続を試みられる余地が生まれる
（実際にはトークン Cookie が `SameSite=Strict` のため送られず失敗するが、防壁は重ねる）。

`X-Forwarded-Host` を信頼するのは、サーバーが `127.0.0.1` でしか待ち受けておらず、
外部からこのヘッダーを任意に付与できないため。

**追記（レビュー反映）**: `X-Forwarded-Host` を採用するのは `Host` がループバックの場合、
つまりプロキシ経由で届いたリクエストに限定する。直接アクセスされたリクエストが
転送ヘッダーを自称しても採用しない。

**未確認事項**: VS Code Port Forwarding が `Host` ヘッダーをどう扱うか（トンネルのホスト名を
そのまま渡すのか、`localhost:<port>` へ書き換えるのか）は実機未確認である。
どちらでも通るよう `Host` と `X-Forwarded-Host` の両方を候補にしているが、
どちらとも一致しない構成では 403 になる。その場合も許可範囲は広げず、
README のトラブルシューティングで状況を説明する方針とする。

## D-006: セッショントークンは HttpOnly Cookie で受け渡す

**判断**: ペアリング成功時に `Set-Cookie: termwatch_session=<token>; HttpOnly; SameSite=Strict; Path=/`
（HTTPS 経由なら `Secure` 付き）を返し、WebSocket のアップグレード時に Cookie を検証する。

**理由**:

- URL にトークンを載せない（要件 8.3）。
- `HttpOnly` により、万一の XSS でもトークンを JavaScript から読めない。
- `SameSite=Strict` によりクロスサイトからのリクエストに付与されない。
- ページを再読み込みしても再ペアリングが不要（ペアリングコードは初回成功で失効するため、
  Cookie を使わないと再読み込みのたびに TermWatch の再起動が必要になってしまう）。

**代替案**: WebSocket の最初のメッセージでトークンを送る方式も検討したが、
リロード耐性がないため採用しなかった。

## D-007: 複数行テキストは bracketed paste で送る

**判断**: リモートから送られたテキストに改行が含まれる場合、`ESC[200~ ... ESC[201~` で囲む。
**貼り付けブロックの内側の改行は LF のまま**送る。単一行の場合は bracketed paste で囲まない。
`submit` が真なら、本文とは**別の書き込み**で確定の CR を送る（下記の経緯を参照）。

**修正の経緯（MT-09 で2回の不合格を経て確定）**

実機確認で2段階の不具合が出た。いずれも推測ではなく、実際に Codex を起動して
PTY 出力を採取・計測して原因を確定させた。

**1回目**: 内側の改行を CR にしていたため、「2行の指示が改行位置で分割され、
2つの指示として同時に渡る」状態だった。`--record` で PTY 出力を採取すると
`ESC[?2004h` が含まれており、**bracketed paste 自体は有効**と分かった。
原因はマーカーではなく改行バイトで、CR が Enter として解釈されていた。
→ 内側を LF に変更。

**2回目**: 今度は「2行が1つの入力として入るが、確定されず、
利用者が追加で Enter を押す必要がある」状態になった。
計測用ハーネスで比較したところ、次が分かった。

| 送り方 | 結果 |
|---|---|
| 本文と確定の CR を**同じ書き込み**で送る | 確定されない |
| 本文を送ってから**別の書き込み**で CR を送る | 確定される |

受け手の TUI は PTY をチャンク単位で読むため、本文と同じ読み取りに入った CR を
本文の一部として吸収してしまい、Enter キーとして扱われない。

**3回目**: 「複数行のときだけ遅らせる」実装にしたところ、今度は単一行が確定しなくなった。
単一行・複数行を問わず、CR は本文とは別の書き込みで送る必要があると分かった。

さらに固定時間（120ms / 250ms）で遅らせる方式は、同じ条件でも確定したりしなかったりと
**計測結果が安定しなかった**。相手の描画速度や処理タイミングに左右されるためと考えられる。

そこで時間ではなく事象を待つ方式へ変更した。本文を書いたあと、
**PTY から出力が届いた（＝ TUI が再描画した＝入力を処理し終えた）ことを検知し、
描画が落ち着いてから**確定の CR を送る。出力が観測できない場合に備えて上限時間も置く。

- `SUBMIT_SETTLE_MS = 80`: 再描画が落ち着いたとみなすまでの待ち時間
- `SUBMIT_FALLBACK_MS = 600`: 再描画を観測できない場合の上限

**この方式の実機確認は利用者に委ねている。** 計測用ハーネスによる自動判定は
結果が安定せず、私の側で「確実に動く」と言い切れる証拠が得られなかったためである。

**副作用**: 確定の CR が最大 600ms 遅れるため、その間に PC 側から入力があると
PTY へ到達する順序が入れ替わりうる。人間の操作速度では実質的に問題にならないと判断した。

**利用者向けの逃げ道**: 万一確定されなかった場合でも、
特殊キーバーの `Enter` を押せば確定できる（この経路は実機で動作確認済み）。

## D-008: PC 側への「リモート操作中」通知はウィンドウタイトルで行う

**判断**: 操作権の有無が変化したとき、標準出力へ OSC 2（`ESC]2;<title>BEL`）を書き、
ウィンドウタイトルを `TermWatch: <コマンド> [リモート操作モード有効]` に変更する。
ターミナルの画面領域には一切書き込まない。

**理由**: 要件 9.3 は「PC 側ターミナルに、スマートフォンが操作モード中であることを表示する。
ただし子プロセスの TUI を壊さない方法で通知する」と定めている。
画面へ直接書き込むと Codex のようなフルスクリーン TUI の描画を破壊する。
OSC 2 は画面バッファを変更しないため安全である。

**制約**: 子プロセスが自分でタイトルを設定する場合、TermWatch の表示が上書きされることがある。
これに対しては 2 秒ごとにタイトルを書き直して対処する。

**重要な追記（実機で見つかった不具合）**: 当初はこの書き直しを無条件に行っていたが、
PC 側で矢印キーが効かなくなり `[?2004h` のような断片が画面に出る不具合が発生した。

原因は、タイトルの書き込みが**子プロセスの出力の途中に割り込む**ことだった。
PTY 出力は任意の位置でチャンクに分割されて届くため、1 つのエスケープシーケンスが
2 つのチャンクにまたがることがある。その隙間にタイトル（`ESC]2;...BEL`）を書くと、
端末はタイトル部分を消費し、残った断片を**ただの文字列として表示**してしまう。

対策として、タイトルは「直近 60ms 以内に PTY 出力が無い」ときだけ書くようにした。
書けなかった更新は保留し、出力が落ち着いてから書き直す。
また、表示すべき内容（ペアリングコード・操作モード）が無いときは periodic な
書き直しを一切行わない。これにより、通常利用時の書き込み回数はほぼゼロになる。
また `--local-only` 時や非 TTY 環境ではタイトル更新を行わない。

**追記（MT-02 の指摘を受けて）**: ペアリングコードもタイトルへ表示するようにした。
起動バナーだけでは、子プロセスが画面消去（`ESC[2J`）を行った時点でコードが読めなくなり、
あとからスマートフォンを接続したいときに詰む（実際に `codex resume --last` で発生した）。
タイトルは画面バッファと独立しているため、消去の影響を受けない。
コードは認証成功または 10 分の期限切れでタイトルからも消える。

なお、コードをファイルへ書き出す案は採らなかった。要件 8.3 が
「ペアリングコードとトークンを URL、通常ログ、アクセスログへ含めない」と定めており、
ディスクへ残す方式はその方針に反するためである。

## D-009: 遅いクライアントにはスナップショット再送でバックプレッシャーをかける

**判断**: 送信前に `ws.bufferedAmount` を確認し、4 MiB を超えていたらそのクライアントを
「遅延中」と印を付けてライブ配信を停止する。200 ms ごとに確認し、512 KiB まで下がったら
`snapshotSince(lastSentSeq)` を送って追いつかせる。

**理由**: 低速回線のクライアント向けに未送信データを溜め続けると、TermWatch のメモリが
無制限に増える。溜めずに「後でまとめて現在の状態を送る」ことで、メモリ上限は
リングバッファのサイズに収まる。遅延中に破棄された出力があれば `truncated: true` で通知される。

## D-010: 操作権はサーバー生成の秘密ハンドルで識別する

**判断**: 操作権を付与するとき、サーバーが `randomBytes(24)` のハンドルを生成し、
所有クライアントにだけ返す。再接続時は `resume { controlHandle }` でこのハンドルを提示させる。

**理由**: 60 秒以内の再接続で操作権を維持する要件（9.2）を満たすには、
WebSocket 接続をまたぐ識別子が必要になる。クライアントが自称する ID を使うと、
同じセッションに接続した別の端末が他人の操作権を乗っ取れてしまう。
サーバー生成の秘密値にすることでこれを防いだ。

## D-011: ポート競合時は自動変更せず終了する

**判断**: 指定ポートが使用中（`EADDRINUSE`）の場合、別ポートへ自動変更せず、
メッセージを表示して終了コード 3 で終了する。子プロセスは起動しない。

**理由**: 要件 11 が「別ポートへ勝手に変更せず、使用中であることを表示する」と定めている。
利用者は VS Code の Ports ビューで転送するポート番号を手動設定するため、
勝手にポートが変わると転送設定と食い違って混乱する。
またサーバーの起動を子プロセスより先に行うことで、起動できなかった場合に
子プロセスを孤児として残さない。

## D-012: Web UI では Enter を送信に割り当てない

**判断**: テキストエリア内の Enter は常に改行として扱い、送信は「送信」ボタンだけで行う。

**理由**: 要件 7.1 は複数行入力を前提としている。日本語 IME の変換確定でも Enter が
発生するため、Enter を送信に割り当てると変換確定のたびに誤送信される。

---

## D-013: ポータブル版は node.exe を単体で同梱する

**判断**: Node.js ランタイムとして、ビルドに使用した `node.exe` を 1 ファイルだけ
`runtime/node.exe` へコピーする。単一 EXE 化（SEA、pkg 等）は行わない。

**理由**: Windows の `node.exe` は単体で動作する。`node-pty` はネイティブモジュールを含むため
単一 EXE 化が難しく、実装指示でも「単一EXE化に固執しない」ことが認められている。

**ABI 互換性**: `node-pty` の同梱プリビルド（`prebuilds/win32-x64`）は
`node-addon-api`（N-API）版であり、N-API の ABI は Node.js のバージョン間で安定している。
そのため、ビルド環境と実行環境の Node.js バージョンが厳密に一致しなくても動作する見込みである。
ただし**別 PC での実機確認は未実施**である（`docs/MANUAL_TESTS_WINDOWS.md` の MT-14 を参照）。

## D-014: 「出力停止中」の判定は 3 秒の無出力

**判断**: 子プロセスが生存しており、最終出力から 3 秒以上経過している場合を `idle`（出力停止中）とする。
UI には「出力停止中」と最終出力からの経過時間を併記し、「入力待ち」とは表示しない。

**理由**: 要件 10 が「出力停止中」を「一定時間出力がない」で定義しつつ、意味解析を禁じている。
3 秒はプロンプト待ちを素早く反映しつつ、通常の処理の切れ目で頻繁に切り替わりすぎない値として選んだ。

## D-015: コードレビュー（Codex）で指摘された点への対応

外部レビューを実施し、指摘のうちバグ・セキュリティに該当するものを修正した。対応内容:

| 指摘 | 対応 |
|---|---|
| `X-Forwarded-Host` を無条件に信頼していた | `Host` がループバックの場合（＝プロキシ経由）に限って採用するよう限定（D-005 を更新） |
| 操作権の期限判定が 1 秒ごとの tick だけで、期限直後の入力が通りうる | `ControlManager.isHolder()` が期限も判定するようにし、入力のたびに検査する |
| `resume` を繰り返すと最大 64 MiB のスナップショットを何度も生成できる | `resume` は 1 接続につき 1 回だけ許可し、2 回目は close(1008) |
| 同時接続数が無制限 | 上限 8 接続。超過時は 503 で拒否 |
| HTTP / WebSocket ハンドラーの例外がプロセスを落としうる | それぞれに例外境界を追加 |
| keep-alive 接続が残ると `server.close()` が返らない | 1 秒でタイムアウトし、`terminate()` と `closeAllConnections()` で強制終了 |
| slowloris 的な接続の放置 | `headersTimeout` / `requestTimeout` / `keepAliveTimeout` を設定 |
| 半開き接続が検出されず操作権が解放されない | 30 秒ごとの ping/pong による生存確認を追加 |
| `PtySession` の `'error'` イベントに購読者がおらず、発火するとプロセスが落ちる | `'warning'` イベントへ変更し、`main.ts` で購読 |
| `pty.write()` の例外が未捕捉 | try/catch で `'warning'` へ変換 |
| `--record` の書き込み中エラー（非同期）が未捕捉 | ストリームの `error` を購読し、記録を停止して継続 |
| 終了猶予タイマーを `unref()` していたため、通知前にプロセスが終了しうる | `unref()` を外した |
| `process.exit()` で標準出力が切り捨てられうる | `process.exitCode` を設定し、100ms の猶予後に終了 |
| ローカル標準入力を chunk ごとに `toString('utf8')` していたため、日本語がチャンク境界で化けうる | `StringDecoder` を使用 |
| Web UI が古い WebSocket のコールバックを処理しうる／多重接続 | 世代番号による無効化と、接続時の旧ソケット破棄を追加 |
| 401 でのハンドシェイク失敗はブラウザに close code 1006 としか伝わらず、永久に再接続し続ける | 切断時に `/api/session` で認証状態を確認し、失効していればペアリング画面へ戻す |
| 出力配信でクライアントごとにバッファ全体を走査していた | 通常経路（連番が連続する場合）は当該チャンクのみ送信 |

**対応しなかった指摘**:

- **`.cmd` / `.bat` 経由の引数が cmd.exe に再解釈されうる**（D-001 参照）。
  `& | < > % ! ^ ( )` を含む引数が分割・展開される可能性がある。
  ただしこれは利用者自身が入力したコマンドラインに限られ、リモートの攻撃者が
  操作できる経路ではない（リモートからは PTY への入力しか送れず、コマンドラインは変更できない）。
  npm シムの実体を解析して `node.exe script.js` へ直接展開する案もあるが、
  npm のバージョン間で形式が変わるため壊れやすい。現状は制約として文書化するにとどめる。
- **全クライアントが同一のセッショントークンを共有する**。端末単位の識別・失効はできない。
  MVP は「単一利用者が自分の端末から使う」前提であり、要件でも端末ごとの管理は求められていない。
  操作権はトークンとは別のハンドルで排他制御しているため、要件 11 は満たされる。

## D-018: PC側入力は、途中で切れたエスケープシーケンスを結合してから渡す

**判断**: PC の標準入力から受け取ったデータのうち、末尾が未完のエスケープシーケンス
（`ESC` 単独、終端していない CSI など）である場合は、最大 20ms だけ保持して
続きが届いてからまとめて PTY へ書き込む。通常の文字は保持せず即座に送る。

**理由（実機で見つかった不具合）**: リモート操作モード中に PC 側で矢印キーを押すと、
矢印が機能せず `[A` `[B` のような文字が入力される不具合が発生した。

矢印キーは `ESC[A` の 3 バイトだが、端末はこれを分割して届けることがある。
Codex は win32 input mode（`ESC[?9001h`）を有効にしており、ConPTY は
**書き込み単位でキー入力へ変換する**。そのため `ESC` と `[A` が別々の書き込みになると、
「Esc キー押下」＋「文字 `[`」＋「文字 `A`」と解釈されてしまう。

スマートフォン接続中に顕著だったのは、配信処理でイベントループが忙しくなり、
標準入力の読み取りが分割されやすくなるためと考えられる。

**遅延への影響**: 保持するのはエスケープシーケンスの途中だけで、通常の文字入力は
一切遅延しない。単独の Esc キー押下は 20ms 後に送られるが、体感できる差ではない。

**関連**: 出力方向の同種の問題（タイトル書き込みがエスケープシーケンスへ割り込む）は
D-008 に記載している。入力・出力のどちらも「エスケープシーケンスを分断しない」ことが要点である。

## D-016: 起動スクリプトは `.cmd` のみとし、`.ps1` は同梱しない

**判断**: ポータブル版には `termwatch.cmd` だけを置く。PowerShell 用の `termwatch.ps1` は同梱しない。

**理由**: PowerShell は PATH からコマンドを解決する際、`.ps1` を `.cmd` より優先する。
両方を置くと `termwatch` が `termwatch.ps1` に解決され、既定の実行ポリシー
（Restricted / RemoteSigned）ではスクリプトの読み込みが拒否されて起動できない。

```text
termwatch : このシステムではスクリプトの実行が無効になっているため、
ファイル ...\termwatch.ps1 を読み込むことができません。
```

`termwatch.cmd` は PowerShell からもコマンドプロンプトからもそのまま実行できるため、
`.cmd` に一本化することでこの問題を回避した。

**あわせて**: 引数なしで起動された場合（エクスプローラーからのダブルクリックなど）は、
ヘルプを表示して `pause` で停止する。以前は使い方エラーを表示した直後にウィンドウが閉じ、
利用者が原因を読めなかった。

## D-019: PC側入力の win32 input mode を復号してからPTYへ渡す

**現象**: リモート操作モード中、PC側で矢印キーを押すと `[A` `[B` `[C` `[D` が入力される。

**経緯**: D-018 で「エスケープシーケンスが分割して届いている」と推測し、
結合バッファを実装したが解消しなかった。推測を重ねるのをやめ、
入力経路に診断記録（`src/pty/input-trace.ts`、環境変数 `TERMWATCH_DEBUG_INPUT` で opt-in）を
入れて実測したところ、分割は起きておらず、届いていたのは次の内容だった。

```
stdin受信 len=45 <ESC>[0;0;27;1;0;1_<ESC>[0;0;91;1;0;1_<ESC>[0;0;65;1;0;1_
```

**原因**: 子プロセス（Codex）が出す `ESC[?9001h`（win32 input mode 要求）は、
TermWatch を素通りして VS Code のターミナルまで届く。以降ターミナルは
`CSI Vk ; Sc ; Uc ; Kd ; Cs ; Rc _` 形式でキー入力を送ってくるが、
矢印キーは仮想キーコードを伴わず、`ESC` `[` `A` の3文字ぶんのレコードへ分解される
(`Vk=0`, `Uc=27` / `91` / `65`)。これをそのまま ConPTY へ渡すと3打鍵として扱われ、
子プロセスには「Escキー」＋文字 `[` ＋文字 `A` として届く。

比較のため、Ctrl+C は `Vk=67`, `Uc=3` を伴うため正しく機能していた
（`<ESC>[67;0;3;1;8;1_<ESC>[67;0;3;0;8;1_`）。これが MT-10 が合格していた理由。

**決定**: `decodeWin32InputMode()` で、PC側入力のレコードを生のバイト列へ復号してから
PTY へ書き込む。上記の3レコードは `ESC[A` の3バイトへ戻り、ConPTY が本来のキーへ変換する。

- 離すイベント（`Kd=0`）は捨てる。押下と両方を採用すると二重入力になる。
- 文字を伴わないキー（`Uc=0`、Shift 単独など）は捨てる。
- 繰り返し回数 `Rc` のぶんだけ複製する（上限 1024）。
- 項目が6つそろわないものは win32 input mode ではないとみなし、手を触れない。

復号はPC側入力にのみ適用する。リモートからの入力は通常のVTバイト列で届くため対象外。

**D-018 の扱い**: 結合バッファはこの不具合の原因ではなかったが、
エスケープシーケンスが分割して届くこと自体は起こり得るため残す。害はない。

**診断記録について**: 既定では無効。有効化中はPC側で入力したキーがそのまま
ファイルへ残るため、起動時に警告を表示する。

## D-020: 子プロセスの終了コードをPC側にも表示する

**現象**: MT-15（子プロセス異常終了）で発覚。子プロセスをタスクマネージャーから
強制終了すると、TermWatch は正しく終了コードを引き継いで終了する（プロセスの
終了コードとして伝播する）が、**PC側のターミナルには何も表示されなかった**。

受け入れ基準 13 は「終了コードが PC 側とスマートフォン側へ表示される」を求めており、
スマートフォン側（`web/src/main.ts`）は実装済みだったが、PC 側が欠落していた。
`docs/ACCEPTANCE_RESULTS.md` で 13 を合格としていたのは、統合テストが
WebSocket 経由の通知しか検証していなかったため。

**決定**: `buildExitNotice()` を追加し、`cleanup()` の後にPC側へ1行表示する。

- `cleanup()` の**後**に書く。raw mode とカーソルを戻してから書かないと、
  子プロセスの TUI の残骸に紛れて読めない。
- 正常終了（0）でも省略しない。強制終了された場合はこの表示だけが手掛かりになり、
  「出ていない＝正常」と読み違える余地を作らないため。
- シグナルがある場合は併記する。

**副次**: バッファ上限超過時の `truncated` 通知が、リングバッファ単体でしか
検証されていなかったため、WebSocket 経由で通知されることの統合テストを追加した。

## D-021: 通信断では再接続を諦めず、経過時間を併記する

**現象**: MT-15（転送停止）で、VS Code の Ports から転送を削除しても
iPhone は「再接続中」のままで、手順書が期待していた「PC未接続」表示にならなかった。

**調査**: 不具合ではなく、手順書の期待結果が実装と食い違っていた。
`Connection` は指数バックオフ（上限 15 秒）で**無期限に**再接続を試みる。
`closed`（「PC未接続」）は `connection.stop()` を呼んだときだけの状態で、
これは子プロセス終了時に使う。

**判断**: 無期限リトライは維持する。瞬断やスリープ復帰で諦めると、
その都度リロードが必要になり、外出先からの利用という目的に反する。

ただし「再接続中」のままでは、数秒の瞬断なのか転送が失われたのかを
利用者が区別できない。利用者へ選択肢を提示し、**経過時間の併記**を採用した。

- 表示: `再接続中（1分20秒）`
- 30 秒を超えたら警告色（`meta danger`）へ変える
- 再接続の動作自体は変更しない

**副次**: `ConnectionState` の定義を `connection-label.ts` へ移した。
`connection.ts` は `window` や `WebSocket` を使うため、そこから型を取ると
単体テストに DOM 型が必要になる。表示ロジックを DOM 非依存に切り出して
テスト対象にした。

**手順書**: `docs/MANUAL_TESTS_WINDOWS.md` の MT-15「転送停止」の期待結果を実装に合わせて修正した。

## D-022: ペアリングコードの入力欄で区切りを自動挿入する

**きっかけ**: 「ハイフンを入力しなければならないのが煩わしい」との指摘。

**確認**: ハイフンは元から入力不要だった。`normalizePairingCode()` が
小文字・ハイフン・半角空白・全角空白・文字集合外の文字をすべて落としてから
照合しているため、`abcd2345` でも `ABCD-2345` でも通る。

問題は表示側で、入力欄のプレースホルダーが `XXXX-XXXX` だったため
「ハイフンが必須」と読めてしまっていた。実装の許容範囲を UI が伝えていなかった。

**決定**: 利用者へ選択肢を提示し、**入力中の自動整形**を採用した。
8文字を続けて打つと `ABCD-EFGH` の形へ整形される。PC 側の表示と見た目がそろうため、
見比べながら打てる。小文字と文字集合外の文字もこの時点で吸収する。

- 区切りを消そうとしたときは、その手前の1文字も一緒に消す。
  そうしないと即座に再挿入され、消せないように見える。
- カーソル位置は「コード文字を何個ぶん進んだか」で数え直す。
  整形で文字数が変わるため、単純な位置指定では途中編集でずれる。
- `maxlength` を 16 から 9 へ狭めた（整形後の最大長）。

**副次**: 文字集合・正規化・整形を `src/shared/pairing.ts` へ移した。
`src/security/tokens.ts` は `node:crypto` を使うため Web バンドルから読み込めず、
そのままではスマートフォン側で同じ正規化を再実装することになり、
定義がずれる恐れがあった。`tokens.ts` からは再輸出しているため既存の import は変わらない。

## D-023〜D-027: コードレビュー（Codex・2回目）で指摘された点への対応

D-015 以降の変更（D-016〜D-022）について Codex のレビューを受けた。
重大な指摘は無く、中5件・軽微5件。すべて対応した。

### D-023: win32 input mode のレコードは Vk=0 かつ Sc=0 のものだけ畳む

**指摘**: `Uc=0` のレコードを一律に捨てていたため、Ctrl+Space やファンクションキーなど
「文字を伴わないが意味のあるキー」が無入力になる。また項目は末尾から省略でき、
`ESC[65;30;97;1_` も正規のレコードだが、6項目未満を拒否していたため取りこぼす。

**調査**: ConPTY の入力パーサーは win32 input mode のレコードを**自分で解釈できる**。
D-019 の不具合は「VS Code が矢印キーを Vk=0 の文字レコード3個へ分解して送る」ことが
原因であり、ConPTY はそれを忠実に3打鍵として渡していた。
つまり Vk を持つレコードは畳まず素通しするのが正しい。

**決定**: 畳むのは `Vk=0` かつ `Sc=0` の文字レコードのみ。それ以外は手を触れない。
項目数は1〜6を受理し、省略分は `Kd=0` / `Cs=0` / `Rc=1` の既定値とする。
7項目以上は別物として素通しする。

この変更で、指摘3（貼り付け本文に紛れたレコード形式の誤変換）も同時に解消した。
`ESC[1;2;65;1;0;2_` は `Vk=1` を持つため書き換え対象外になる。

### D-024: タイトル書き込みは出力の解析状態が ground のときだけ

**指摘**: 60ms の静止判定では、PTY が `ESC[` を出したまま待機した場合に
未完のシーケンスへ OSC が割り込む。D-008 の不具合が残る。

**決定**: 出力チャンクを跨いでエスケープシーケンスの解析状態を保持する
（`nextVtState()`）。`ground` のときだけタイトルを書く。
静止時間は補助条件として残す。

### D-025: 「本文→確定Enter」を直列化する

**指摘**: 各送信が独立に確定Enterを待つため、80ms 以内に2件送ると
PTY には本文が続けて入ったあとで CR が2つ届き、指示が結合される。

**決定**: セッション単位のキューで直列化する。滞留は32件を上限とし、
超過分は `rate-limited` で拒否する。確定待ちの出力リスナーも集合で保持し、
サーバー終了時に確実に解除する。

### D-026: ビジュアルビューポートのずれを二重に足していた

**指摘**: `offsetTop + (pageTop - scrollY)` は同じずれを2回数えている。

**決定**: `offsetTop` のみを使う。MT-17 で表面化しなかったのは、
`body` を固定しているため両者とも 0 だったため。潜在的な不具合として修正した。

### D-027: 再接続の経過時間と入力欄の細部

- 画面復帰時の即時再接続は backoff を初期化して `connecting` を通るため、
  状態名だけで判定すると経過時間がリセットされる。
  「一度でも接続できたか」を保持して判定する。
- ペアリング入力欄は IME 変換中（`isComposing`）に書き換えない。
  未確定文字列が消える。確定時（`compositionend`）にまとめて整形する。
- 区切りの削除は `deleteContentBackward` と `deleteContentForward` を分ける。
  一括で「手前を消す」と、Delete キーで意図しない文字が消える。

### D-028: 診断記録の警告を実態に合わせる

**指摘**: 警告は「このPCで入力したキー」としていたが、記録は `PtySession.write()` で
行うため、スマートフォンから送った本文も平文で残る。

**決定**: 警告文を「PC側とスマートフォン双方の入力が残る」「パスワードやAPIキーも
対象になる」「共有しない」「調査後は削除する」と具体化した。
新規作成時のファイル権限を所有者のみ（0o600）に絞る。

## D-029: 出力停止のプッシュ通知（Web Push・WebSocket接続有無での抑制）

**判断**: iPhone がホーム画面へ追加した PWA として開かれている場合に限り、
子プロセスの出力が一定時間（既定 30 秒、`--notify-idle-seconds`）止まったことを
Web Push で通知する。通知本文にはコマンド名と出力停止からの経過時間だけを載せ、
ターミナルの内容は一切含めない。`--no-notify` で無効化できる。

**なぜ Web Push しかないか**: 画面を閉じた（または他アプリに切り替えた）iOS の Safari へ
何かを届ける手段は、iOS 16.4 以降が対応した Web Push 以外に存在しない。
WebSocket や Server-Sent Events は、画面を閉じるとページごと停止するため使えない。
Web Push は OS のプッシュサービス経由で配信されるため、ページが動いていなくても届く。
ただし iOS の実装上、**ホーム画面へ追加した PWA としてでないと通知を受け取れない**
（Safari のタブのままでは `Notification` の許可自体が求められない）。
これは TermWatch の設計選択ではなく iOS 側の制約であり、
`docs/MANUAL_TESTS_WINDOWS.md` の MT-18 と README にホーム画面への追加を必須として明記した。

**通知本文を最小限にした理由**: Web Push の本文は VAPID 鍵による端末間暗号化
（RFC 8291）がかかっており、配信網（Apple Push Notification service）の運営者は
平文を読めない。しかし暗号化は「途中経路で読まれない」ことを保証するだけで、
**内容が PC の外（Apple のサーバーを経由してスマートフォンの通知センター）へ出ること自体は
変わらない**。通知センターの表示はロック画面でも他人に見えるため、要件 8.3 が
禁じている「ターミナル内容の露出」に抵触しうる。そのためコマンド名と経過時間のみに絞った
（`src/notify/push-sender.ts` の `buildIdlePayload`）。

**「画面を見ている間は送らない」判定に WebSocket の接続有無を使う**: 通知送信の直前に
`server.activeClientCount`（認証済み WebSocket 接続数）を確認し、1 台以上いれば送らない。
新しいプロトコル（Page Visibility API の値をサーバーへ送る、等）を追加せずに済むのは、
iOS が**画面を閉じる（バックグラウンドへ回る）と WebSocket 接続を切る**という挙動に
乗っているため。

**この前提は実機で確認済み（2026-08-13）**。iPhone の画面を閉じた状態で
「codex の出力が30秒止まっています」の通知が届き、抑制が解除されることを確認した。

なお抑制は端末を区別しない。接続中の端末が1台でもあれば送らないため、
PC のブラウザで TermWatch を開いたままにしていると通知は止まる。

**永続状態について**: TermWatch にとって初めて、プロセス終了後も残るファイルを持つ
（`src/notify/paths.ts` の `configDir()`、既定 `%APPDATA%\TermWatch`）。
置くのは VAPID 鍵（`push-sender.ts`）と購読情報（endpoint・鍵、`subscription-store.ts`）
の 2 種類のみで、ターミナルの内容や送受信履歴は保存しない。`--record` の
「既定では何も保存しない」という方針（D-標準）は変えていない。

**`web-push` パッケージを追加した理由**: Web Push の暗号化（RFC 8291 aes128gcm）は
ECDH 鍵合意・HKDF・AES-GCM を正しい順序・パラメータで組み合わせる必要があり、
自前実装は実装ミスが暗号強度の低下に直結しやすい（鍵導出やソルト・カウンターの
扱いを誤ると保護が実質的に無効化されうる）。`web-push` は広く使われている
リファレンス実装であり、自前実装によるリスクを負う理由がない。

**ファイル権限について**: `loadOrCreateVapidKeys()` と `SubscriptionStore` は
書き込み時に `mode: 0o600` を指定している。**この指定は Windows では他利用者からの
読み取りを制限しない**（Windows のファイルアクセス制御は POSIX パーミッションビットではなく
ACL で行われ、Node.js の `mode` オプションは Windows 上ではほぼ効果を持たない）。
実際の保護は権限ビットではなく**置き場所**、すなわち `%APPDATA%\TermWatch` による。
`%APPDATA%` は利用者ごとのプロファイル配下にあり、Windows の既定 ACL で
他の利用者アカウントからのアクセスが制限される。`mode: 0o600` を残しているのは、
将来 Linux/macOS 環境で動かす場合に意味を持たせるためであり、
Windows 上での保護効果を主張するものではない。

**要件との関係**: `TermWatch_Requirements_v1.0.md` 第4.2章「MVPに含めない機能」は
「iOSプッシュ通知」を明示的に対象外としていた。本機能は第18章「将来拡張候補」の
「出力停止・終了時の通知」として、MVP完成後の拡張として実装した
（「終了時の通知」は対象外のまま。子プロセス終了と同時に TermWatch 自体も終了するため、
その時点でプッシュ通知を送っても開く先が存在しない）。

## D-030: `handlePairRequest` に `error` イベント処理が無かった不具合

**現象**: Task 9（本タスク）で購読 API の実装を見直していたところ、
出荷済みの `handlePairRequest`（`src/server/server.ts`）にはリクエスト本文を
読み取る処理があるが、`IncomingMessage` の `'error'` イベントを購読していないことに気づいた。

**何が起きうるか**: クライアントがペアリングリクエストの送信途中で切断すると、
`req`（`IncomingMessage`）は `'error'` を発火する。Node.js の `EventEmitter` は
`'error'` イベントに購読者がいない場合、そのエラーを例外として再スローする仕様のため、
未購読のままだと**プロセス全体が落ちる**。TermWatch は単一プロセスで PTY・WebSocket・
子プロセスすべてを抱えているため、これはターミナル操作中の利用者にとって
「理由の分からない全断」として現れる。ネットワークが不安定なスマートフォン接続では
現実的に起こりうる経路であり、攻撃を要さない。

**対応**: 本文読み取りの共通処理を `consumeBody()` として切り出し、
`data` / `end` に加えて `error` も必ず購読するようにした。エラー時は `aborted` フラグを立てて
以後の応答・処理を止める（切断済みの接続へ書き込むとさらに例外を招くため）。
`handlePairRequest` と購読 API（`handlePushRequest` 経由の `readJsonBody`）の
両方をこの共通処理に統一した。

**確認**: 統合テストで、リクエスト送信途中にソケットを破棄したあともサーバーが
生存し続け、後続のリクエストに応答できることを固定した（`tests/integration/push-api.test.ts`）。

## D-031: ポータブル版の同梱依存を自動で解決し、漏れを検査する

**現象**: プッシュ通知の追加後、`C:\tools\TermWatch` に配置した TermWatch が
起動時に落ちるようになった。

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'web-push'
    imported from C:\tools\TermWatch\app\notify\push-sender.js
```

`npm run package:win` は成功していた。

**原因**: `scripts/package-win.mjs` が同梱するモジュールを手書きで列挙していた
（`['node-pty', 'ws', 'node-addon-api']`）。依存を1つ増やしたときに追記が必要だと
気づける仕組みが無く、`web-push` とその推移的依存 17 件が丸ごと抜けた。

**決定**: 列挙をやめ、`package.json` の `dependencies` から推移的にたどって同梱する。
併せてライセンス一覧も、手書きではなく実際に同梱したものから生成する。

**検査について**: 当初は「同梱版を実際に起動してみる」確認を入れたが、**これは機能しない**。
出力先が `dist/` すなわちリポジトリ配下にあるため、Node はモジュールを見つけられないと
親ディレクトリへ遡り、開発機の `node_modules` から解決してしまう。
実際に `web-push` を取り除いても `--version` は成功した。
手元では通り、配置先でだけ落ちるため、確認として役に立たない。

そのため、実行ではなく**同梱物の静的検査**に変えた。
`dist/app` 配下の `.js` からパッケージ名の import を集め、
すべてが出力先の `node_modules` にあることを確かめる。
`web-push` を `dependencies` から外して実際に検証し、終了コード 1 で止まることを確認した。

**教訓**: 「ビルドが成功した」ことと「配置先で動く」ことは別である。
検証がリポジトリの中で行われる限り、リポジトリの中身に助けられていないかを疑う必要がある。

## D-032: 通知が届かなかった2つの原因

**現象**: 実機で「通知を有効にする」まで成功し購読も保存されていたが、
出力を止めても iPhone に通知が届かなかった。

保存された購読を使って手元から直接送信し、原因を切り分けた。

### 原因1: プロキシを使っていなかった

直接送信すると `AggregateError [ETIMEDOUT]` で、Apple のサーバーへ TCP 接続すらできていなかった。
社内ネットワークでは外向き通信がプロキシ必須で、`HTTPS_PROXY` が設定されている。

**`web-push` は環境変数のプロキシ設定を自分では読まない。** 明示的に渡す必要がある。
渡したところ `ETIMEDOUT` から `403` へ変わり、到達自体は解決した。

**決定**: `proxyFromEnv()` で `HTTPS_PROXY` / `https_proxy` / `HTTP_PROXY` / `http_proxy` を
読み、送信時に渡す。**この値には資格情報が含まれることがあるため、ログへ一切出さない。**

### 原因2: VAPID の subject が到達しない宛先だった

到達後も `403 {"reason":"BadJwtToken"}` が返った。subject を変えて実測したところ:

| subject | 結果 |
|---|---|
| `mailto:termwatch@localhost` | 403 BadJwtToken |
| 実在するメールアドレス | 201 成功 |
| `https://github.com/mattaku1582670/TermWatch` | 201 成功 |

Apple は到達しない宛先を受け付けない。設計時に「実在のアドレスを持たないため
ローカルを指す」としたのは誤りだった。

**決定**: プロジェクトの URL を使う。個人情報を埋め込まずに済む。

### 併せて修正: 403 で購読を消さない

送信失敗時の削除対象に 403 を含めていたが、これは誤りだった。
今回の `BadJwtToken` のように、403 は**こちら側の設定ミス**でも返る。
403 で消すと、設定を直すまでの間に正常な購読が失われ、
利用者は毎回スマートフォンから登録し直すことになる。

RFC 8030 で「購読が消えた」を意味するのは 404 と 410 だけ。削除はこの2つに限る。

### 教訓

いずれもコードからは読み取れない外部サービスの制約であり、
単体テスト・統合テストをいくら足しても検出できなかった。
**外部と通信する機能は、実際に通信してみるまで動作を主張できない。**
再発を防ぐため、subject が `localhost` を含まないこと、
プロキシを環境変数から読むことを単体テストで固定した。
