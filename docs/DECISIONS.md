# 実装上の判断記録（DECISIONS）

要件定義書（`TermWatch_Requirements_v1.0.md`）と実装指示に明記されていない細部について、
実装時に行った判断とその理由を記録する。

---

## D-001: 実行コマンドの解決に PATH / PATHEXT の自前探索を使う

**判断**: `node-pty` へ渡す実行ファイルを、PATH と PATHEXT を自前で探索して解決する。
`.cmd` / `.bat` の場合だけ `cmd.exe /d /s /c <実体パス> <引数...>` の形で起動する。

**理由**: Windows の `CreateProcess` はバッチファイルを直接実行できない。
`codex` や `claude` は npm の bin シム（`.cmd`）であることが多く、直接指定すると起動に失敗する。

**安全性**: いずれの場合も引数は argv 配列のまま渡し、コマンド文字列を結合しない。
`/d` で AutoRun（レジストリの `Command Processor\AutoRun`）を無効化する。
`.ps1` の直接実行は拒否し、`powershell -File` を使うよう案内する。

---

## D-002: 出力バッファはチャンク単位で保持し、破棄もチャンク境界で行う

**判断**: リングバッファは「行」ではなく PTY から受け取ったチャンクを単位として保持する。
表示行数の上限はチャンク内の改行数を数えて近似的に適用し、加えて総バイト数の上限
（既定は `maxLines * 512`、最小 1 MiB、最大 64 MiB）も設ける。直近 1 チャンクは
上限を超えていても破棄しない。

**理由**: 行単位で切ると ANSI エスケープシーケンスの途中で分断され、
再接続時にスナップショットを流し込んだ際の描画が壊れる。実装指示でも
「行数ベースのリングバッファ実装がANSIシーケンスの途中切断を招く場合は、
安全なチャンク保持と表示行上限を組み合わせる」ことが許容されている。

**副作用**: 保持される表示行数は指定値ちょうどではなく「指定値以下の直近チャンク群」になる。
また、改行を含まない巨大な単一チャンクはバイト上限まで保持される。
1 つの ANSI シーケンスが 2 チャンクにまたがって届いた場合、その境界で破棄が起きると
分断されうる（頻度は極めて低く、xterm.js 側が不完全なシーケンスを読み捨てる）。

---

## D-003: スナップショットとライブ出力の境界にシーケンス番号を使う

**判断**: 各出力チャンクへ 1 から始まる単調増加のシーケンス番号を割り当てる。

- クライアントは接続直後に `resume { lastSeq }` を送る。
- サーバーは `snapshotSince(lastSeq)` の結果を `snapshot { data, seq, truncated }` として返す。
- 以後のライブ出力は `output { data, seq }` で送り、クライアントは `lastSeq` を更新する。
- 要求範囲の一部が既に破棄されている場合は `truncated: true` を立て、欠落を隠さない。

**理由**: スナップショット送信中に発生した出力の取りこぼしや二重表示を防ぐため。
サーバーは `resume` を受け取るまでそのクライアントへ配信を開始しない（`ready` フラグ）ので、
スナップショットより前のライブ出力が混ざることもない。

## D-004: ペアリングコードは 30 文字集合 × 8 文字（約 39.2 bit）

**判断**:

| 項目 | 値 |
|---|---|
| 文字集合 | `23456789ABCDEFGHJKMNPQRSTVWXYZ`（Crockford Base32 から `0` `1` を除いた 30 文字） |
| 長さ | 8 文字（表示は `XXXX-XXXX`） |
| エントロピー | log2(30^8) ≒ **39.2 bit** |
| 有効期限 | 起動から 10 分、または最初の認証成功の早い方 |

**理由**: Crockford Base32 は `I` `L` `O` `U` を既に除外している。さらに `0` `1` を除くことで
`0`/`O`、`1`/`I` の読み間違いを完全に排除し、スマートフォンでの手入力を容易にした。
8 文字はハイフン区切りで一目で読める上限に近い。

39.2 bit は単独では総当たり可能な水準だが、
(1) dev tunnels のアカウント認証を通過した攻撃者にしか試行機会がない、
(2) 連続 5 回の失敗でロックアウト（30 秒から倍化、上限 15 分）、
(3) 有効期限が 10 分、
の 3 点により実効的な総当たりは成立しない。

## D-005: Origin 検証は同一オリジンのみ。devtunnels のワイルドカード許可はしない

**判断**: `Origin` のホスト部が `Host` または `X-Forwarded-Host` と一致する場合だけ許可する。
`*.devtunnels.ms` のようなワイルドカード許可は**行わない**。`Origin` が無い接続は拒否する。

**理由**: ワイルドカードを許すと、攻撃者が自分の dev tunnel 上に置いたページから
利用者の `127.0.0.1:43821` へクロスサイト WebSocket 接続を試みられる余地が生まれる
（実際にはトークン Cookie が `SameSite=Strict` のため送られず失敗するが、防壁は重ねる）。

`X-Forwarded-Host` を信頼するのは、サーバーが `127.0.0.1` でしか待ち受けておらず、
外部からこのヘッダーを任意に付与できないため。

**追記（レビュー反映）**: `X-Forwarded-Host` を採用するのは `Host` がループバックの場合、
つまりプロキシ経由で届いたリクエストに限定する。直接アクセスされたリクエストが
転送ヘッダーを自称しても採用しない。

**未確認事項**: VS Code Port Forwarding が `Host` ヘッダーをどう扱うか（トンネルのホスト名を
そのまま渡すのか、`localhost:<port>` へ書き換えるのか）は実機未確認である。
どちらでも通るよう `Host` と `X-Forwarded-Host` の両方を候補にしているが、
どちらとも一致しない構成では 403 になる。その場合も許可範囲は広げず、
README のトラブルシューティングで状況を説明する方針とする。

## D-006: セッショントークンは HttpOnly Cookie で受け渡す

**判断**: ペアリング成功時に `Set-Cookie: termwatch_session=<token>; HttpOnly; SameSite=Strict; Path=/`
（HTTPS 経由なら `Secure` 付き）を返し、WebSocket のアップグレード時に Cookie を検証する。

**理由**:

- URL にトークンを載せない（要件 8.3）。
- `HttpOnly` により、万一の XSS でもトークンを JavaScript から読めない。
- `SameSite=Strict` によりクロスサイトからのリクエストに付与されない。
- ページを再読み込みしても再ペアリングが不要（ペアリングコードは初回成功で失効するため、
  Cookie を使わないと再読み込みのたびに TermWatch の再起動が必要になってしまう）。

**代替案**: WebSocket の最初のメッセージでトークンを送る方式も検討したが、
リロード耐性がないため採用しなかった。

---

## D-007: 複数行テキストは bracketed paste で送る

**判断**: リモートから送られたテキストに改行が含まれる場合、`ESC[200~ ... ESC[201~` で囲む。
**貼り付けブロックの内側の改行は LF のまま**送り、`submit` が真なら
**ブロックの外側**に CR を1つ追加する。単一行の場合は bracketed paste で囲まない。

**修正の経緯（MT-09 の不合格を受けて）**: 当初は内側の改行も CR へ変換していたが、
実機確認で「2行の指示が、改行位置で分割された2つの指示として同時に渡る」不具合が発生した。
Codex CLI の PTY 出力を `--record` で採取したところ `ESC[?2004h` が確認でき、
**bracketed paste 自体は有効**だった。したがって原因はマーカーではなく改行バイトで、
受け手の TUI が貼り付け内容中の CR を Enter キーとして解釈し、その位置で確定していた。

貼り付け内容の改行は LF で表現するのが一般的（クリップボード由来のテキストと同じ）であり、
「確定」はブロック外の CR で表現する。これにより、内容全体が1つの指示として渡る。

**理由**: TUI が行単位で読み取ると、複数行テキストの途中の改行が「確定」として扱われ、
1 行目だけが送信されてしまう。bracketed paste は「これは貼り付けであって入力確定ではない」
ことを伝える標準的な手段で、Codex CLI や Claude Code のような TUI は概ね対応している。

**フォールバック**: bracketed paste 非対応のアプリでは `[200~` のような文字列が
そのまま入力欄に現れる。この挙動は README の「既知の制約」に記載し、
1 行ずつ送信する回避策を案内する。端末側の対応可否を確実に検出する手段が
サーバー側にないため、自動フォールバックは実装していない。

## D-008: PC 側への「リモート操作中」通知はウィンドウタイトルで行う

**判断**: 操作権の有無が変化したとき、標準出力へ OSC 2（`ESC]2;<title>BEL`）を書き、
ウィンドウタイトルを `TermWatch: <コマンド> [リモート操作モード有効]` に変更する。
ターミナルの画面領域には一切書き込まない。

**理由**: 要件 9.3 は「PC 側ターミナルに、スマートフォンが操作モード中であることを表示する。
ただし子プロセスの TUI を壊さない方法で通知する」と定めている。
画面へ直接書き込むと Codex のようなフルスクリーン TUI の描画を破壊する。
OSC 2 は画面バッファを変更しないため安全である。

**制約**: 子プロセスが自分でタイトルを設定する場合、TermWatch の表示が上書きされることがある。
また `--local-only` 時や非 TTY 環境ではタイトル更新を行わない。

## D-009: 遅いクライアントにはスナップショット再送でバックプレッシャーをかける

**判断**: 送信前に `ws.bufferedAmount` を確認し、4 MiB を超えていたらそのクライアントを
「遅延中」と印を付けてライブ配信を停止する。200 ms ごとに確認し、512 KiB まで下がったら
`snapshotSince(lastSentSeq)` を送って追いつかせる。

**理由**: 低速回線のクライアント向けに未送信データを溜め続けると、TermWatch のメモリが
無制限に増える。溜めずに「後でまとめて現在の状態を送る」ことで、メモリ上限は
リングバッファのサイズに収まる。遅延中に破棄された出力があれば `truncated: true` で通知される。

## D-010: 操作権はサーバー生成の秘密ハンドルで識別する

**判断**: 操作権を付与するとき、サーバーが `randomBytes(24)` のハンドルを生成し、
所有クライアントにだけ返す。再接続時は `resume { controlHandle }` でこのハンドルを提示させる。

**理由**: 60 秒以内の再接続で操作権を維持する要件（9.2）を満たすには、
WebSocket 接続をまたぐ識別子が必要になる。クライアントが自称する ID を使うと、
同じセッションに接続した別の端末が他人の操作権を乗っ取れてしまう。
サーバー生成の秘密値にすることでこれを防いだ。

---

## D-011: ポート競合時は自動変更せず終了する

**判断**: 指定ポートが使用中（`EADDRINUSE`）の場合、別ポートへ自動変更せず、
メッセージを表示して終了コード 3 で終了する。子プロセスは起動しない。

**理由**: 要件 11 が「別ポートへ勝手に変更せず、使用中であることを表示する」と定めている。
利用者は VS Code の Ports ビューで転送するポート番号を手動設定するため、
勝手にポートが変わると転送設定と食い違って混乱する。
またサーバーの起動を子プロセスより先に行うことで、起動できなかった場合に
子プロセスを孤児として残さない。

---

## D-012: Web UI では Enter を送信に割り当てない

**判断**: テキストエリア内の Enter は常に改行として扱い、送信は「送信」ボタンだけで行う。

**理由**: 要件 7.1 は複数行入力を前提としている。日本語 IME の変換確定でも Enter が
発生するため、Enter を送信に割り当てると変換確定のたびに誤送信される。

---

## D-013: ポータブル版は node.exe を単体で同梱する

**判断**: Node.js ランタイムとして、ビルドに使用した `node.exe` を 1 ファイルだけ
`runtime/node.exe` へコピーする。単一 EXE 化（SEA、pkg 等）は行わない。

**理由**: Windows の `node.exe` は単体で動作する。`node-pty` はネイティブモジュールを含むため
単一 EXE 化が難しく、実装指示でも「単一EXE化に固執しない」ことが認められている。

**ABI 互換性**: `node-pty` の同梱プリビルド（`prebuilds/win32-x64`）は
`node-addon-api`（N-API）版であり、N-API の ABI は Node.js のバージョン間で安定している。
そのため、ビルド環境と実行環境の Node.js バージョンが厳密に一致しなくても動作する見込みである。
ただし**別 PC での実機確認は未実施**である（`docs/MANUAL_TESTS_WINDOWS.md` の MT-14 を参照）。

## D-014: 「出力停止中」の判定は 3 秒の無出力

**判断**: 子プロセスが生存しており、最終出力から 3 秒以上経過している場合を `idle`（出力停止中）とする。
UI には「出力停止中」と最終出力からの経過時間を併記し、「入力待ち」とは表示しない。

**理由**: 要件 10 が「出力停止中」を「一定時間出力がない」で定義しつつ、意味解析を禁じている。
3 秒はプロンプト待ちを素早く反映しつつ、通常の処理の切れ目で頻繁に切り替わりすぎない値として選んだ。

## D-015: コードレビュー（Codex）で指摘された点への対応

外部レビューを実施し、指摘のうちバグ・セキュリティに該当するものを修正した。対応内容:

| 指摘 | 対応 |
|---|---|
| `X-Forwarded-Host` を無条件に信頼していた | `Host` がループバックの場合（＝プロキシ経由）に限って採用するよう限定（D-005 を更新） |
| 操作権の期限判定が 1 秒ごとの tick だけで、期限直後の入力が通りうる | `ControlManager.isHolder()` が期限も判定するようにし、入力のたびに検査する |
| `resume` を繰り返すと最大 64 MiB のスナップショットを何度も生成できる | `resume` は 1 接続につき 1 回だけ許可し、2 回目は close(1008) |
| 同時接続数が無制限 | 上限 8 接続。超過時は 503 で拒否 |
| HTTP / WebSocket ハンドラーの例外がプロセスを落としうる | それぞれに例外境界を追加 |
| keep-alive 接続が残ると `server.close()` が返らない | 1 秒でタイムアウトし、`terminate()` と `closeAllConnections()` で強制終了 |
| slowloris 的な接続の放置 | `headersTimeout` / `requestTimeout` / `keepAliveTimeout` を設定 |
| 半開き接続が検出されず操作権が解放されない | 30 秒ごとの ping/pong による生存確認を追加 |
| `PtySession` の `'error'` イベントに購読者がおらず、発火するとプロセスが落ちる | `'warning'` イベントへ変更し、`main.ts` で購読 |
| `pty.write()` の例外が未捕捉 | try/catch で `'warning'` へ変換 |
| `--record` の書き込み中エラー（非同期）が未捕捉 | ストリームの `error` を購読し、記録を停止して継続 |
| 終了猶予タイマーを `unref()` していたため、通知前にプロセスが終了しうる | `unref()` を外した |
| `process.exit()` で標準出力が切り捨てられうる | `process.exitCode` を設定し、100ms の猶予後に終了 |
| ローカル標準入力を chunk ごとに `toString('utf8')` していたため、日本語がチャンク境界で化けうる | `StringDecoder` を使用 |
| Web UI が古い WebSocket のコールバックを処理しうる／多重接続 | 世代番号による無効化と、接続時の旧ソケット破棄を追加 |
| 401 でのハンドシェイク失敗はブラウザに close code 1006 としか伝わらず、永久に再接続し続ける | 切断時に `/api/session` で認証状態を確認し、失効していればペアリング画面へ戻す |
| 出力配信でクライアントごとにバッファ全体を走査していた | 通常経路（連番が連続する場合）は当該チャンクのみ送信 |

**対応しなかった指摘**:

- **`.cmd` / `.bat` 経由の引数が cmd.exe に再解釈されうる**（D-001 参照）。
  `& | < > % ! ^ ( )` を含む引数が分割・展開される可能性がある。
  ただしこれは利用者自身が入力したコマンドラインに限られ、リモートの攻撃者が
  操作できる経路ではない（リモートからは PTY への入力しか送れず、コマンドラインは変更できない）。
  npm シムの実体を解析して `node.exe script.js` へ直接展開する案もあるが、
  npm のバージョン間で形式が変わるため壊れやすい。現状は制約として文書化するにとどめる。
- **全クライアントが同一のセッショントークンを共有する**。端末単位の識別・失効はできない。
  MVP は「単一利用者が自分の端末から使う」前提であり、要件でも端末ごとの管理は求められていない。
  操作権はトークンとは別のハンドルで排他制御しているため、要件 11 は満たされる。

## D-016: 起動スクリプトは `.cmd` のみとし、`.ps1` は同梱しない

**判断**: ポータブル版には `termwatch.cmd` だけを置く。PowerShell 用の `termwatch.ps1` は同梱しない。

**理由**: PowerShell は PATH からコマンドを解決する際、`.ps1` を `.cmd` より優先する。
両方を置くと `termwatch` が `termwatch.ps1` に解決され、既定の実行ポリシー
（Restricted / RemoteSigned）ではスクリプトの読み込みが拒否されて起動できない。

```text
termwatch : このシステムではスクリプトの実行が無効になっているため、
ファイル ...\termwatch.ps1 を読み込むことができません。
```

`termwatch.cmd` は PowerShell からもコマンドプロンプトからもそのまま実行できるため、
`.cmd` に一本化することでこの問題を回避した。

**あわせて**: 引数なしで起動された場合（エクスプローラーからのダブルクリックなど）は、
ヘルプを表示して `pause` で停止する。以前は使い方エラーを表示した直後にウィンドウが閉じ、
利用者が原因を読めなかった。

## D-017: 統合テストの `AttachConsole failed` について

**現象**: vitest（コンソールを持たないフォークプロセス）で `pty.kill()` を呼ぶと、
`node-pty` の補助プロセス `conpty_console_list_agent.js` が
`Error: AttachConsole failed` を標準エラーへ出力する。

**判断**: TermWatch 側の不具合ではなく、テストも失敗しないため対処しない。
実際のターミナルから起動した場合はコンソールが存在するため発生しない。
